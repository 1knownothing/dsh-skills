# references/orchestration.md — 在 DSH 里编排这套流程

> 核心立场：**本 skill 就是 Supervisor。** 不要再写一层 agent 调度器。

---

## 1. 为什么不要自己实现编排层

原流程图（Supervisor Agent + LangGraph 状态图 + 三个并行产出）在 **LangGraph 语境**下是合理的：
那里没有现成的编排原语，必须自己画状态图。

但 DSH 已经提供：

| 需求 | DSH 现成原语 |
|---|---|
| 起独立上下文的执行者 | `subagent` / `spawn_teammate` |
| 批量独立扇出（N 个文件/N 个角度） | `workflow` 脚本（pipeline/parallel） |
| 共享任务板 + 依赖 + 写作用域 | `team_task_*` / Agent Teams |
| 跨轮次保持目标 | `create_goal` |
| 长命令不阻塞 | 后台 job |
| 把结果变成可见交付物 | `present` |

自己再实现一层"Supervisor 循环"只会带来：多一层不可观测的失败点、状态同步 bug、调不动的问题。
**用平台原语表达流程，用本 skill 约束纪律。**

## 2. 三种编排形态怎么选

| 形态 | 什么时候用 | DSH 原语 |
|---|---|---|
| **单线串行** | 阶段有强依赖（S1→S2→S3→S4→S5→S6→S7） | 当前会话按 skill 逐阶段走 |
| **并行切片** | 多片改动互相独立（不同文件/模块） | Agent Teams：每片一 owner，写作用域互斥，`blocked_by` 表达依赖 |
| **批量扇出** | 同一动作重复 N 次（审计 N 文件、多角度调研、迁移 N 处） | `workflow` 脚本，**不要**逐个手动委派 |

**并行前提**：写入范围必须互斥。重叠 → 串行，或者重新切片。

## 3. 独立验证者怎么起

### 方式 A：`subagent`（推荐，一次性）
```
subagent(
  description="独立验证 T1",
  prompt="""
你是独立验证者，不参与实现，也不负责让它通过。

## 验收标准（原文，不许改）
AC1 …
AC2 …

## 产物位置
- 代码：<路径>
- 测试：<路径>

## 你要做的
1. 跑 L1→L4，逐条命令 + 原始输出
2. 主动找反例
3. 反向对照：故意破坏一处，确认断言变红
4. 逐条判定：通过/不通过/未验证
5. 给出最可能挂的 3 个场景

## 禁止
不许改实现代码让测试通过；不许放宽验收标准。
"""
)
```

### 方式 B：Agent Teams（长时间、多验证者）
- 建共享任务「独立验证 <T1>」，owner = 专职验证者
- 验证者的报告**只回 Lead**，不直接改代码
- Lead 收齐后跑最终验收

### 关键
- 验证者**拿不到**实现者的自我评价
- 验证者拿的是 **S1 验收标准原文**
- 验证者的产出（verify.md）**进验收报告**

## 4. Lead 的职责边界

做：
- 定验收标准（S1）
- 定切片与写作用域（S4）
- 分派 + 收集 + 裁决冲突
- **跑最终端到端验证**（不能只听队友说"好了"）
- 给用户的最终交付说明

不做：
- 不替队友写他负责的文件（写作用域冲突）
- 不在队友还在跑时给最终结论
- 不用"某队友说通过了"代替自己看 diff 和跑测试

---

## 5. 长任务与跨会话

- **目标跨轮次**：`create_goal`，目标写成"可判完成的验收结果"，不是"努力方向"
- **状态落盘**：阶段进度写 `.agent/<task-slug>/`，**不依赖会话记忆**
- 会话被压缩/恢复后：读 `.agent/<task-slug>/` 就知道走到哪了
- 卡片式交付（文档/表格/PPT/图）用 `present`，不要只把文件路径写在正文里

---

## 6. 成本与延迟（别忽略）

多智能体/多阶段**不是免费的**：
- 每个子 Agent 独立上下文 = 独立 token 成本
- 并行扇出的协调成本随宽度上升
- **小任务不要上多 Agent**：改一个函数，直接自己改 + 起一个验证者就够

判断线：
- 任务 < 30 分钟工作量 → 单线，只加独立验证
- 任务跨多文件/多模块 → 切片 + 部分并行
- 任务是 N 个同构子任务 → `workflow` 扇出

---

## 7. 常见编排错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| Lead 把验证也交给自己 | 自证清白 | 独立验证者 |
| 两个 owner 写同一文件 | 互相覆盖、FS_STALE_VERSION | 写作用域互斥或串行 |
| 用 sleep/轮询等队友 | 浪费且不可靠 | 显式依赖 + 等待机制 |
| 并行分支互相需要对方产出 | 上下文断裂（原图的病） | 改成串行或显式依赖 |
| 小任务上 8 个 Agent | 成本爆炸、协调开销大于收益 | 单线 + 1 验证者 |
| 队友说完成就结案 | 未验证的结论进交付 | Lead 自己跑最终验证 |

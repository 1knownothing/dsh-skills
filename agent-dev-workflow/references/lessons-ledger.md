# references/lessons-ledger.md — 把人类否决变成可重放校验

> S8 的核心：**同一个坑只能踩一次。** 只写"下次注意"等于没写。

---

## 1. 为什么需要这一层

原流程图（用户给的图）里，`User Approval` 有一条回退线指向 `Human Review Agent`，
但 `Human Review Agent` 的意见**没有回流到 Supervisor**。

后果：人类认为"Java 测试文件不行"→ 重跑 → **同样的错再犯一次**。
这不是模型能力问题，是**流程缺回路**。

修法不是"让人多审几遍"，而是：
**人类的每一次否决，都要变成下一次自动检查的一部分。**

---

## 2. 三层沉淀（从弱到强）

| 层 | 形式 | 强度 | 什么时候够用 |
|---|---|---|---|
| L1 规则 | 写进项目约定文件的一句话 | 弱（靠自觉） | 无法自动化的判断（如审美） |
| L2 检查清单 | 开工必读的 checklist 条目 | 中 | 人工可执行但无法脚本化 |
| L3 可重放校验 | 测试 / 审计脚本 / 断言 | **强（机器守）** | **能自动化的都必须到这层** |

原则：**能到 L3 就到 L3。** L1/L2 是兜底，不是首选。

---

## 3. 沉淀动作（S8 执行）

1. **提取现象**：人类到底否决了什么？原话是什么？
2. **找根因**：为什么会这样？是缺约束、缺信息、还是缺校验？
3. **写规则**：下次开工必须遵守什么？（一句话，可执行）
4. **写成校验**：哪个命令/测试能守住它？
   - 能写成测试 → 写测试
   - 能写成审计脚本 → 写脚本
   - 都不能 → 写进 checklist 并标注"未自动化"
5. **落盘**：写进**项目级**文件（不是会话里）
   - 通用项目约定：`DEVELOPMENT.md` / `CONTRIBUTING.md`
   - 项目已有纪律文档：如本项目的 `docs/22-工程纪律.md`
6. **写清落盘位置**到 `lessons.md`，形成索引

---

## 4. 记录格式

```markdown
## 2026-10-09 生成的测试代码无法编译

- 现象：AI 产出的 Java 测试直接进 User Approval，人一跑就编译失败；
        下一轮重跑仍然犯同样的错。
- 根因：流程没有"编译即门禁"，生成产物直接进入人工审查；
        人的否决没有回流成约束。
- 规则：任何代码产物必须先过 L1 静态层（编译/lint），
        未过不许进入人工审查。
- 校验：`mvn -q test-compile` 退出码必须为 0
        （已加入 CI 前置步骤 / `tools/check_compile.py`）
- 落盘：`DEVELOPMENT.md` §3.2
```

## 5. 反面清单

| 病 | 症状 | 修法 |
|---|---|---|
| 口号化 | "以后要注意边界条件" | 改成"边界用例必须写成测试" |
| 会话内 | 教训只写在对话里 | 必须落项目文件 |
| 无校验 | 写了一堆规则，没有一条可执行 | 至少标注"未自动化"并排期 |
| 灌水 | 每次都给项目文档加一节 | 只写**新**教训，重复的合并 |
| 错层 | 能自动化的却只写了句提醒 | 下沉到 L3 |
| 无索引 | 规则散落各处 | `lessons.md` 做索引 + 落盘位置 |

## 6. 项目级文件的最小骨架

若项目还没有约定文件，创建 `DEVELOPMENT.md`：

```markdown
# 开发纪律

> 本文件是**开工必读**。每次因人类否决或验收失败产生新教训，追加一条。

## 硬约束（违反即返工）
1. …

## 验收口径
- 功能改动：必须过 L1 静态 + L2 单元 + L3 真实入口
- 数据/内容改动：必须过守恒审计（`tools/audit_*.py`）

## 教训台账
### <日期> <标题>
- 现象 / 根因 / 规则 / 校验
```

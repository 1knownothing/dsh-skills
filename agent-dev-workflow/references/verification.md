# references/verification.md — 独立验证方法论

> 验证的目的不是"确认没问题"，是**找反例**。找不到反例才算通过。

---

## 1. 为什么必须独立

实现者验证自己的产出，存在结构性利益冲突：他脑中的"预期行为"和代码里的"实际行为"已经绑定，会不自觉地把**已知现象**当成**正确现象**。

本项目真实教训（`docs/13`）：端点换回 DeepSeek 官方前后，同一份代码"看起来都在正常运行"，
但校内网关时期是**正文被思考吃空**的静默失败——只有换端点、量 token、跑对照才暴露。

**独立验证的三条硬要求**：
1. 验证者上下文里**没有**实现者的自我评价（不给"我觉得已经修好了"）
2. 验证者拿到的是 **S1 的验收标准原文**，不是实现者转述的目标
3. 验证者有权说"不通过"，且**不承担"让结果变绿"的压力**

## 2. 四层验证

| 层 | 命令类型 | 通过标志 | 防的是什么 |
|---|---|---|---|
| L1 静态 | 编译 / lint / 类型检查 / 格式检查 | 退出码 0 | 低级错误、语法错、未使用变量 |
| L2 单元 | 目标模块测试 | 相关测试全绿，断言数达标 | 逻辑错、边界没处理 |
| L3 端到端 | 真实入口完整跑一次 | 有**真实产物**：日志/文件/截图/退出码 | mock 掩盖的集成错 |
| L4 验收 | 对照 S1 每条标准 | 逐条可判真假 + 产物路径 | 做对了但**没做对的事** |

### 层间顺序不可跳
编译都过不了就别谈验收；单元测试红了说明逻辑没对，端到端的结果不可信。

### L3 的"真实产物"是什么
- 进程退出码 + 完整 stdout/stderr
- 生成的文件（路径 + 大小 + 关键内容片段）
- 截图 / 报表 / 数据库查询结果
- 网络请求记录（状态码 + 响应体片段）

**只跑 mock 不算 L3。** 必须至少有一次真实依赖参与。

## 3. 反向对照（最重要的一条）

一个**从没红过的测试**等于没有测试。

做法：故意破坏一处（改坏一个常量、删一个校验、把返回值翻过来），
跑测试，**断言必须变红**。不变红 → 测试是装饰 → 打回重写。

本项目正例（`docs/13`）：`test_step35` 里包含"摘掉一条 op → 对应功能不再执行"的反向对照；
`test_step39` 里包含"切回 baseline → 静态段在动态段之前全红"。

### 反向对照清单
- [ ] 删掉核心校验 → 测试必须红
- [ ] 把边界条件改成差一 → 测试必须红
- [ ] 把输出字段改名 → 金标比对必须红
- [ ] 把异常吞掉 → 对应断言必须红

## 4. 验证者任务书模板

给独立验证者（`subagent` 或新会话）的消息模板：

```
你是独立验证者，不参与实现，也不负责让它通过。

## 验收标准（逐条判定，不许改标准）
<粘贴 S1 的 AC1..ACn 原文>

## 产物位置
- 代码：<路径>
- 测试：<路径>
- 证据：.agent/<task>/evidence.md

## 你要做的
1. 跑 L1 → L4，逐条命令 + **原始输出**贴进 verify.md
2. 主动找反例：什么输入会挂？哪个边界没覆盖？改坏了什么？
3. 做反向对照：故意破坏一处，确认断言会红（列出你破坏了什么）
4. 逐条给判定：通过 / 不通过 / 未验证（三态）
5. 最后给"最可能挂的 3 个场景"

## 禁止
- 不许修改实现代码来让测试通过
- 不许放宽或改写验收标准
- 不许写"看起来没问题"这种结论
```

## 5. 失败分类（决定回哪一阶段）

| 类别 | 判据 | 动作 | 禁止 |
|---|---|---|---|
| A 环境/依赖 | 命令找不到、依赖缺失、权限、端口占用 | 修环境，重跑**同一**命令 | 改代码迁就坏环境 |
| B 规格歧义 | 代码没错但和 AC 对不上 | 回 S1 显式修订标准 + 说明 | 偷偷放宽标准 |
| C 实现缺陷 | 断言失败、边界未处理 | 回 S5 改实现 + **加回归断言** | 只改测试 |
| D 设计缺陷 | 补丁越打越乱，根因在结构 | 回 S3/S4 重切 | 在错结构上继续补 |
| E 验证错误 | 测试写错、夹具错、断言过严 | 修验证 + 说明理由 | 删掉碍事的测试 |

### 重试策略
- 同类别**最多 3 次**自动重试
- 每次重试必须**有新的信息或假设**（纯重复同一动作不算重试）
- 超限 → 停止，升级给人：

```
## 需要你决定
- 目标：<原目标>
- 卡在：<类别 + 具体现象>
- 已试：1) … 结果 …  2) … 结果 …  3) … 结果 …
- 我的判断：<最可能的根因>
- 可选方向：
  A. …（代价 …，风险 …）
  B. …（代价 …，风险 …）
  C. 降级目标为 …（代价：交付缩水）
```

**打转比失败更贵**：3 次没进展就说明当前假设是错的，继续试只是在烧时间。

## 6. 验收报告格式

```markdown
# verify.md — <task>

## 环境
- 命令版本、基线 commit、时间

## L1 静态
$ <命令>
<原始输出>

判定：✅ 通过

## L2 单元
$ <命令>
<原始输出>

判定：✅ 通过（断言数 63）

## L3 端到端
$ <命令>
<原始输出 / 产物路径 + 关键片段>

判定：⚠️ 部分——产物生成了，但 #3 场景退出码 1（见下）

## L4 验收
| 标准 | 判定 | 证据 |
|---|---|---|
| AC1 | ✅ | 上面的 L1 输出 |
| AC2 | ❌ | 报错：… |
| AC3 | ⚠️ 未验证 | 需要真实设备 |

## 反向对照
- 破坏：把 <位置> 的校验删掉 → test_xxx 变红 ✅（证明测试有效）

## 最可能挂的 3 个场景
1. …
2. …
3. …

## 失败分类
- AC2 属 C 类（实现缺陷），应回 S5 修 src/xxx.py:120
```

## 7. 反面清单

| 病 | 症状 |
|---|---|
| 自证 | 实现者自己写"已通过" |
| 假绿 | 测试从没红过 |
| 只看测试 | 单元绿就说功能好了，没跑过真实入口 |
| 转述输出 | 不贴原始输出，只说"输出正常" |
| 放宽标准 | 测试不过就改测试 |
| 打转 | 同一错误重试 10 次 |
| 沉默失败 | 异常被吞、默认值兜底、裁剪数据，都不报告 |

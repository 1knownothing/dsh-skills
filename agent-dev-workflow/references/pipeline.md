## S1 需求澄清与验收定义

### 检查清单
- [ ] 用**一句话**复述目标，用户能指着说"对/不对"
- [ ] 列出所有**可判真假**的验收标准（每条带验证命令）
- [ ] 写明**范围外**（这次明确不做的事）
- [ ] 识别并问掉所有会导致返工的歧义（≥3 种解释时必须问）
- [ ] 确认约束：目标平台、运行环境、性能/成本/时间预算、不能动的部分
- [ ] 确认交付形态：代码？文档？可执行产物？装到哪？

### 验收标准的写法
**不合格**：
```
- 界面更好用
- 性能优化
- 代码更清晰
```
**合格**：
```
- AC1 给定空输入，执行 `python tools/check_script.py --all`，退出码 0，输出不含 FAIL
- AC2 给定 200 条场景，`pytest tests/test_step40.py` 全绿（≥63 条断言）
- AC3 启动后 5 秒内可访问 http://127.0.0.1:19387 且返回 200
```
判据：**换一个人拿到这条标准，能独立判定通过与否**。

### 歧义处理
用 `ask_user_question`，给选项而不是问开放题：
- 差：“你想要什么样的性能？”
- 好：“目标延迟取哪个档？① 交互级 <200ms ② 分钟级批处理 ③ 只要不超时即可”

## S2 现状勘查

### 检查清单
- [ ] 找到目标功能的**现有实现在哪**（文件:行号）
- [ ] 找到**谁调用它**（上游），**它调用谁**（下游）
- [ ] 找到**现有测试/审计脚本**，确认改动会不会踩到金标
- [ ] 找到**同类已解决问题的既有方案**（优先复用）
- [ ] 确认版本控制状态与基线（能否回退）
- [ ] 记录**看不见的接线**：配置、环境变量、注册表、约定文件

### 产物格式
```
## 现状
- 入口：src/core/ops.py:120 `run_ops()` — 统一分发 14 条 op
- 调用方：src/core/turn_engine.py:474 / 721 / 1429 …
- 既有测试：tools/test_step40.py（63 条）
- 可复用：ops.Op.validate(ctx) 已是统一校验入口

## 改动影响面
- 改 ops.py 的 run_ops 会影响 6 处调用点 → 需回归 test_step35/40
- register.json 结构被 3 处读取 → 不能改字段名

## 基线
- git rev: <hash>，工作区干净 / 有未提交改动（列出）
```

### 禁止
- 不读代码就写"我理解了现有架构"
- 结论里没有 文件:行号
- 用"大概/应该/通常是这样"充当事实

## S4 任务切片

### 切片原则
- 每片能**独立验证**（有自己的验收命令）
- 每片写入范围**互不重叠**（重叠就必须串行）
- 依赖关系**显式声明**，不靠"假设前一片已做完"
- 单片过大（>1 小时工作量）就再切

### 任务卡格式
```
T1 [owner] 目标：…
   写入范围：src/core/ops.py, tests/test_step41.py
   验收：python -m pytest tests/test_step41.py -q  → 全绿
   依赖：无
T2 [owner] 目标：…
   写入范围：docs/30-*.md
   验收：文档含 X/Y/Z 三节
   依赖：T1（需要 T1 的最终接口）
```

### 并行约束
- 同一文件**不能**两个 owner 同时写
- 共享资源（端口、数据库、构建目录、缓存）要显式排它
- 用平台原语表达依赖（Agent Teams 的 `blocked_by`），不要用"我 sleep 等它"

## S5 实现

### 检查清单
- [ ] 一次只做一片；做完立刻跑该片验收
- [ ] 改动行数与目标匹配（改 200 行只为修 1 个 typo → 有问题）
- [ ] 没夹带无关重构、格式化、重命名
- [ ] 新增行为配了新增断言
- [ ] 每步证据落 `evidence.md`（命令 + 真实输出）
- [ ] 临时文件/调试打印/被注释代码已清理

### 遇到既有 bug
- 与本次目标无关 → 记进 `lessons.md` 待办，**不夹带修**
- 挡住本次目标 → 升级为独立任务，先修它再做原目标

### 证据格式
```
### 2026-10-09 14:20
$ python -m pytest tests/test_step41.py -q
8 passed in 1.42s

$ python tools/check_redlines.py
OK  0 violations
```

## S6 独立验证

见 `references/verification.md`（完整方法论）。核心：
- 验证者**不参与实现**，只拿验收标准 + 产物位置
- 四层（静态 / 单元 / 端到端 / 验收）逐层跑
- 必须做**反向对照**：故意破坏一处，断言必须变红
- 逐条附**原始输出**，不许转述

## S8 固化教训

### 触发条件
- 人类否决了产出
- S6/S7 出现 A–E 类失败
- 同一个坑第二次踩到

### 动作
1. 写进项目级约定文件（如 `DEVELOPMENT.md` / `docs/22-工程纪律.md`），格式：
   ```
   ## <日期> <教训标题>
   - 现象：（真实发生的事）
   - 根因：（为什么会这样）
   - 规则：（下次开工必须遵守什么）
   - 校验：（哪个命令/测试能守住它）
   ```
2. **能自动化的立刻自动化**：写成测试、审计脚本、断言。只写"下次注意"等于没写。
3. 只写**新**教训；重复的合并进已有条目，不新开。

### 反面
- 把"我以后会小心"当教训
- 教训只写在会话里不落盘（下次会话看不到）
- 写一堆规则但没有任何一条可执行
